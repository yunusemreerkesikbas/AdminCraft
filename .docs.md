# Generic Field Validation System

## 📋 Overview

Reusable, rule-based validation framework for any entity field with fluent builder API.

## 🏗️ Architecture

```
FieldValidator<T>           → Main interface
FieldValidatorBuilder<T>    → Fluent API
ValidationRule<T>           → Individual rule
ValidationContext           → Runtime metadata
ValidationResult            → Result wrapper
```

## 🚀 Quick Start

**1. Configure Validator Bean:**

```java
@Configuration
public class MyModuleValidatorConfig {

    @Bean
    public FieldValidator<String> productSkuValidator() {
        return FieldValidatorBuilder.<String>create()
            .withKeyFormat("^[A-Z]{2,4}-[0-9]{4,8}$", "Invalid SKU format")
            .withLengthConstraint(7, 13)
            .build();
    }

    @Bean
    public FieldValidator<BigDecimal> priceValidator() {
        return FieldValidatorBuilder.<BigDecimal>create()
            .withRangeConstraint(new BigDecimal("0.01"), new BigDecimal("999999.99"))
            .build();
    }
}
```

**2. Use in Service:**

```java
@Service
public class ProductService {

    private final FieldValidator<String> skuValidator;
    private final FieldValidator<BigDecimal> priceValidator;

    public void validateProduct(Product product) {
        ValidationContext context = ValidationContext.empty();
        context.set("existingSkuCount", productRepo.count());

        skuValidator.validate(product.getSku(), context).throwIfInvalid();
        priceValidator.validate(product.getPrice()).throwIfInvalid();
    }
}
```

## 📦 Built-in Rules

| Rule                  | Usage                                                  |
| --------------------- | ------------------------------------------------------ |
| `KeyFormatRule`       | Regex pattern matching (camelCase, snake_case, custom) |
| `ReservedKeywordRule` | Block reserved words                                   |
| `LengthRule`          | String min/max length                                  |
| `RangeRule`           | Numeric min/max value                                  |
| `CountLimitRule`      | Limit based on context count                           |

## 🎯 Builder API

```java
FieldValidatorBuilder.<String>create()
    .withCamelCaseKey(50)
    .withReservedKeywords(Set.of("id", "type", "class"))
    .withCountLimit(100, "existingFieldCount")
    .withCustomRule(myCustomRule)
    .build();
```

## 🔧 Custom Rules

```java
public class UniqueEmailRule implements ValidationRule<String> {
    private final UserRepository userRepo;

    @Override
    public ValidationResult validate(String email, ValidationContext context) {
        if (userRepo.existsByEmail(email)) {
            return ValidationResult.failure("Email already exists");
        }
        return ValidationResult.success();
    }

    @Override
    public String getRuleName() {
        return "UniqueEmail";
    }
}
```

## ✅ Best Practices

- Create validator beans in `@Configuration` classes
- Use `ValidationContext` for runtime metadata (counts, IDs)
- Chain rules with builder pattern
- Reuse validators across services via DI
- Custom rules for domain-specific logic

# ItemDialog - Reusable CRUD Dialog Component

## 📋 Overview

Schema-driven dialog component for Create/Edit operations with multi-language tabs (General + TR/EN).

## 🚀 Quick Start

```typescript
import { ItemDialogService } from "@shared/services/item-dialog.service";

export class MyListComponent {
  #dialogService = inject(ItemDialogService);
  #myService = inject(MyService);
  #notification = inject(NotificationService);

  create(): void {
    const options: ItemDialogOptions<MyDto> = {
      mode: "create",
      titleKey: "admin.myModule.entityName",
      schema: this.#buildSchema(),
      languages: ["tr", "en"],
      initial: {
        status: "DRAFT",
        tr: { title: "", description: "" },
        en: { title: "", description: "" },
      },
    };

    this.#dialogService
      .open<MyDto>(options)
      .pipe(take(1))
      .subscribe((result) => {
        if (!result) return;
        this.#myService
          .create(result)
          .pipe(take(1))
          .subscribe(() => {
            this.#notification.success("admin.messages.createSuccess");
            this.#loadData();
          });
      });
  }

  #buildSchema(): ItemDialogSchema {
    return {
      general: [
        {
          key: "status",
          type: "select",
          labelKey: "admin.fields.status",
          required: true,
          options: [{ value: "ACTIVE", labelKey: "admin.status.active" }],
        },
      ],
      i18n: [
        {
          key: "title",
          type: "text",
          labelKey: "admin.fields.title",
          required: true,
          maxLength: 200,
        },
      ],
    };
  }
}
```

## 📝 Field Types

| Type       | Usage                 |
| ---------- | --------------------- |
| `text`     | Single-line input     |
| `textarea` | Multi-line input      |
| `select`   | Dropdown with options |
| `number`   | Numeric input         |
| `checkbox` | Boolean toggle        |

## 🎯 API

**ItemDialogOptions:**

```typescript
{
  mode: 'create' | 'edit';
  titleKey: string;              // i18n key
  schema: ItemDialogSchema;
  languages: ['tr', 'en'];
  initial?: Partial<TDto>;
  id?: TId;                      // For edit mode
```

**Return Value:**


## Subdomain-Based Tenant Authentication (Sprint 17)

**What Changed:** Tenant users login via subdomain resolution (`democompany.localhost`) instead of path-based routing.

**Problem Solved:** Tenant admin login returned 401 because backend queried `platform_management.users` instead of `ac_tenant_{id}.users`. Root cause: no tenant identifier in request.

### Authentication Flow

**Headers Priority:**

| Priority | Header                            | Use Case                   |
| -------- | --------------------------------- | -------------------------- |
| 2        | `X-Tenant-Subdomain: democompany` | New (recommended)          |
| 3        | None                              | SUPER_ADMIN platform login |

**Special subdomain:** `admin` → Platform admin auth

### Backend: Subdomain Resolution

**Critical Pattern:**

```java
// AuthenticationServiceImpl.java
if (subdomain != null && !subdomain.equals("admin")) {
    Tenant tenant = tenantRepository.findBySubdomain(subdomain);
    validate(tenant.isActive());

    // MUST set context BEFORE UserRepository query
    tenantContext.setTenantId(tenant.getId());
    tenantContext.setTenantDbName(tenant.getDatabaseName());
}

// Now queries correct tenant DB
User user = userRepository.findByEmail(email);
```

**Files Changed:**

- `AuthenticateCommand.java` - Added `subdomain` field
- `AuthController.java` - Reads `@RequestHeader("X-Tenant-Subdomain")`
- `AuthenticationServiceImpl.java` - Tenant resolution logic

### Frontend: Hostname Parsing

**Subdomain Extraction:**


## Tenant DTO Refactor + Auto-Provisioning (Sprint 18)

**What Changed:** Separated tenant DTOs by use case, added auto-provisioning workflow, and optimized polling.

### Bug Fix: Schema Mismatch

**Problem:** V7 migration removed `admin_email`/`admin_name` columns, but `Tenant` entity still mapped them → `SQLGrammarException`

**Solution:**

- Removed `adminEmail`, `adminName` from `Tenant.java`
- Deleted `TenantAdminInfoResponse` (was returning null)
- Removed 4 builder calls from integration tests

### Polling Optimization

**Problem:** Frontend kept polling `/api/provisioning/jobs/{id}` after job completion (5+ unnecessary requests)

**Solution:** Use `takeWhile` to stop polling

```typescript
// module-provision-dialog.component.ts
pollJobStatus(jobId: string): void {
  interval(2000).pipe(
    switchMap(() => this.service.getJobStatus(jobId)),
    takeWhile(job =>
      job.status === 'pending' || job.status === 'running',
      true  // Emit final value
    )
  ).subscribe(/* handle result */);
}
```

```http

DELETE /api/page-templates/{id}         # Delete (non-system)
POST   /api/page-templates/{id}/slots   # Add slot
DELETE /api/page-templates/{id}/slots/{slotName}    # Remove slot
PUT    /api/page-templates/{id}/slots/reorder       # Reorder slots
POST   /api/page-templates/{id}/assign/{pageId}     # Assign to page
```

## 🚀 Frontend Usage

```typescript
import { PageTemplateService } from '@admin/page-templates/page-template.service';

// List templates

```

## 📦 Key Concepts

| Concept         | Description                                              |
| --------------- | -------------------------------------------------------- |
| Template        | Reusable layout (e.g., `homepage-template`)              |

| Auto-creation   | Assign template → auto-creates missing `page_slots`      |
| System template | `isSystem=true`, cannot be deleted or modified           |
| allowedTypes    | `null` = all types, `[]` = none, `["Banner"]` = specific |
