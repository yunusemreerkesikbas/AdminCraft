# AdminCraft vs SAP Hybris: Technical Architecture Analysis

This report provides a technical comparison of the AdminCraft Backoffice architecture against SAP Commerce Cloud (Hybris) standards, specifically focusing on Multi-Language (i18n) handling, API patterns, and integration recommendations.

## 1. Architecture & Data Model

| Area               | SAP Hybris (Enterprise)                        | AdminCraft (Modern SaaS)                             | Assessment                                               |
| :----------------- | :--------------------------------------------- | :--------------------------------------------------- | :------------------------------------------------------- |
| **Data Structure** | Attribute-level (`loc=true`). Large LP tables. | Entity-level (`Base` + `I18n`). Clean SQL structure. | ✅ **AdminCraft**: More modern and performant for RDBMS. |
| **Isolation**      | `BaseStore` + Global Catalog.                  | `Tenant` (Strict Isolation).                         | ✅ **AdminCraft**: Perfect isolation for SaaS.           |
| **Content Model**  | `Page` -> `Slot` -> `Component` (Nested).      | `Page` -> `Slot` -> `Component` (Implemented V12).  | ✅ **AdminCraft**: Slot architecture implemented.         |

## 2. API & Data Management Comparison

### A. Read Strategy (Backoffice Data Fetching)

Strategies used to populate Item Editor (Detail) pages.

| Feature         | AdminCraft (Current)                       | SAP Hybris (Backoffice)                  | Analysis                   |
| :-------------- | :----------------------------------------- | :--------------------------------------- | :------------------------- |
| **Endpoint**    | `GET /api/pages/{id}?include=translations` | `GET /ws/v2/products/{code}?fields=FULL` | ✅ **Equivalent**          |
| **Response**    | Nested JSON (Translation Map)              | Nested JSON (Localized Attributes)       | ✅ **Modern & Compatible** |

### B. Write Strategy (Create/Update) - ⚠️ CRITICAL GAP

Strategies used when creating new content with translations.

| Feature         | AdminCraft (Current)                                                                          | SAP Hybris (Backoffice)                              | Analysis                      |
| :-------------- | :-------------------------------------------------------------------------------------------- | :--------------------------------------------------- | :---------------------------- |
| **Endpoint**    | 1. `POST /api/pages` (Base) <br> 2. `PUT /api/pages/i18n/TR` <br> 3. `PUT /api/pages/i18n/EN` | `POST /ws/v2/products` (Payload includes everything) | ⚠️ **Design Trade-off**       |
| **Payload**     | Fragmented data submission.                                                                   | Single `Composite Payload`.                          | ⚠️ **Network Overhead**       |
| **Transaction** | Each request in own `@Transactional` boundary.                                                | Single Transaction (via OData $batch).               | ⚠️ **Cross-Request Atomicity**|

**Recommended AdminCraft Composite Payload (Hybris Style):**

```json

{
  "slug": "contact-us", // Base Entity Field
  "templateId": 1,
  "translations": {
    // Composite I18n Data
    "TR": { "title": "İletişim", "description": "..." },
    "EN": { "title": "Contact", "description": "..." }
  }
}
```

## 3. Key Differences & Recommendations

### 1. Slot Architecture - ✅ IMPLEMENTED

- **Hybris**: `Page -> ContentSlot -> Component` (3 Layers). Templates define slots, components are assigned to slots.
- **AdminCraft**: `Page -> Slot -> Component` (3 Layers). **Implemented in V12 migration**.
- **Status**: `PageSlotController.java` and database schema already support slot-based architecture.
- **Reference**: `backend/src/main/resources/db/tenant/pagebuilder/V12__page_slots.sql`

### 2. Fallback Mechanism - ✅ PARTIALLY IMPLEMENTED

- **Hybris**: Complex dual-system fallback (Item attributes vs ResourceBundle). Has documented limitations with country locales (e.g., en_DE).
- **AdminCraft**: **Already implements basic fallback** in `PageI18nServiceImpl.getFallbackLanguageI18n()` - returns first available language when requested language missing.
- **Current**: Returns any available language (simple, predictable)
- **Enhancement Opportunity**: Add tenant default language priority
  - Current: `target_lang ?: any_available`
  - Proposed: `target_lang ?: tenant_default ?: any_available`
- **Reference**: `backend/src/main/java/com/backend/application/service/impl/PageI18nServiceImpl.java:152-163`

### 3. Field Level Configuration (`?fields=...`)

- **Hybris**: Uses **PREDEFINED field levels** (NOT arbitrary selection):
  - `?fields=BASIC` (preconfigured field set)
  - `?fields=DEFAULT` (preconfigured field set)
  - `?fields=FULL` (preconfigured field set)
  - Field mappings are centrally configured, not dynamically selected by client
- **AdminCraft**: Fixed DTOs (`PageDetailDto`) + `include` parameter.
- **Verdict**: Both approaches use **controlled, predefined field sets**. AdminCraft's pattern is equivalent and well-suited for Admin Panel environments.

## 4. Execution Plan (Next Steps)

### Priority 1: UX & Transaction Improvements
1.  **Add Composite Create Endpoints**: Implement optional batch endpoints for creating entities with all translations atomically.
   - Endpoint: `POST /api/pages` with `translations: Record<Language, I18nDto>` in payload
   - Service: Wrap in single `@Transactional` boundary
   - Keep existing separate i18n endpoints for UPDATE operations (partial updates)

### Priority 2: Fallback Enhancements
2.  **Enhance Language Fallback**: Add tenant default language priority to existing fallback mechanism.
   - Current: `PageI18nServiceImpl.getFallbackLanguageI18n()` returns first available
   - Enhancement: Prioritize tenant's default language before falling back to any available
   - Add `isFallback` flag in responses to indicate when fallback was used

### Priority 3: Documentation
3.  **Documentation Updates**:
   - Document `?include=translations` pattern in `.docs.md`
   - Add composite create examples to API documentation
   - Document transaction boundaries and atomicity guarantees
