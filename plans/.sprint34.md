## Sprint 34A: i18n Support (Phase 1-3)

### Entity Pattern

- **BaseI18nEntity**: Language-agnostic fields
- **EntityI18n**: Language-specific fields, `@ManyToOne` to Entity
- **Index**: `(entity_id, language)` unique constraint

### Service Pattern

- **Fallback**: Requested Lang → Default (TR) → First Available → Exception
- **Separate Endpoints**: `/i18n/{language}` for partial updates

## Sprint 34B: Composite Endpoints (Phase 2A - Navigation)

Atomic creation/update of Entity + Translations in a single transaction.

### Endpoints Implemented

| Resource        | Create                               | Update                                   |
| --------------- | ------------------------------------ | ---------------------------------------- |
| NavigationNode  | `POST /navigation/nodes/composite`   | `PUT /navigation/nodes/{id}/composite`   |
| NavigationEntry | `POST /navigation/entries/composite` | `PUT /navigation/entries/{id}/composite` |

### Architecture

- **Backend**: Single `@Transactional` method creates/updates base entity and iterates translation map.
- **Frontend**: `forkJoin` removed. `node-dialog` and `entry-dialog` send single composite payload.
- **Validation**: Nested validation (`@Valid`) on translation map. Rollback on any error.

### DTO Pattern

```java
// CreateNodeCompositeRequest
public record CreateNodeCompositeRequest(
    @NotBlank String uid,
    NodePosition position,
    Boolean isVisible,
    Boolean isTab,
    Long parentId,
    @NotNull Map<Language, NavigationNodeI18nRequest> translations
) {}
```

### When to Use Which Endpoint

#### ✅ Use Composite Endpoints When:

- Creating a new entity with initial translations
- Updating multiple languages at once (bulk update)
- Ensuring atomic transaction (all-or-nothing)
- Frontend dialog forms (single API call for better UX)

#### ✅ Use Individual i18n Endpoints (`/i18n/{language}`) When:

- Updating a single language (e.g., fixing a typo in Turkish title)
- Adding a new language to an existing entity
- Partial update workflow (user editing one language at a time)
- Granular control over translation lifecycle

#### Both patterns are supported and maintained

- Frontend currently uses composite pattern for create/update dialogs
- Individual endpoints remain available for targeted operations
- No deprecation planned for either pattern

## Sprint 34D: Composite Endpoints Fixes (Reviewed 2025-12-23)

Fixes applied after Phase 2A Code Review to ensure data integrity.

### 1. Backend Validation

**File**: `NavigationNodeI18nRequest.java`

- Added `@NotBlank` to `title`.
- **Reason**: Prevent creation of "ghost nodes" with empty titles. Consistent with Entry validation.

### 2. Frontend Payload Filtering

**Files**: `node-dialog.component.ts`, `entry-dialog.component.ts`

- **Logic**: Filter out empty strings from translation map before sending.
- **Reason**: Prevent backend validation failure when optional languages are left empty.

## Technical Guides

### i18n Migration Steps

1. Create `V{N}__{entity}_i18n.sql` (Schema + Data Migration)
2. Create `{Entity}I18n` entity & Repository
3. Create Request/Response DTOs
4. Implement Service (`getFallback`, `upsert`)
5. Add Controller endpoints

### Adding New Composite Module (e.g., Phase 2B)

1. Define `Create{Entity}CompositeRequest` & `Update{Entity}CompositeRequest`
2. Define `{Entity}CompositeResponse`
3. Add `@Transactional` composite methods to Service
4. Add Controller endpoints (`/composite`)
5. Update Frontend Service (`customPost`) & Types
6. Refactor Dialogs to use composite call
